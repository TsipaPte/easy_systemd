# 📚 УРОК: Создание systemd-службы

📚 В этом уроке мы научимся создавать свои кастомные `systemd-службы` и управлять ими в Linux. Поехали!

## 1. Что такое systemd?

🌿 `systemd` — это самый главный процесс в Linux. Он имеет доступ и управляет вообще всеми процессами. Наша цель — научиться создавать собственный фоновый процесс (так называемая `systemd-служба`). Но перед началом вспомним все команды `systemd`:

> [!TIP]- Шпаргалка (кто забыл)
> ```bash
> # Добавить службу в автозагрузку
> sudo systemctl enable служба
>
> # Убрать службу из автозагрузки
sudo systemctl disable служба
>
> # Включить службу, если она выключена
> sudo systemctl start служба
> 
> # Выключить службу
> sudo systemctl stop служба
> 
> # Перезагрузить службу
> sudo systemctl restart служба
> 
> # Перечитать файлы конфигурации, без перезапуска. Работает быстрее, чем restart! Не все службы поддерживают reload, часть только restart!
> sudo systemctl reload служба
> 
> # Посмотреть статус
> sudo systemctl status служба
>
> # Если создали новую службу или обновили конфигурацию существующей
> # Кратко: применить все изменения касаемо служб
>
> sudo systemctl daemon-reload
> ```

## 2. Создать службу

🌸 Все наши службы должны располагаться в `/etc/systemd/system` и иметь расширение `.service` (обязательно!). Итоговый путь: `/etc/systemd/system/имя_службы.service`

## 3. Конфигурация файла

🦔 Самое вкусное! Мы создали файл с расширением `.service` в папке `/etc/systemd/system`. Теперь надо его правильно заполнить. Поехали!

📦 Сам файл конфигурации разбит на блоки. Их много, но в большинстве случаях используется только три — `[Unit]`, `[Service]` и `[Install]`:

| Блок | За что отвечает? |
| ---- | ---------------- |
| `[Unit]` | Описание службы и её зависимостей |
| `[Service]` | Как, где и с какими ограничениями (если они есть) её запускать |
| `[Install]` | Настройки и описание что делать, если службу отправят в автозагрузку (`systemctl enable`) |

📕 Синтаксис:

```systemd
[Unit]
Параметр=значение
# И так далее

[Service]
Параметр=значение
# И так далее

[Install]
Параметр=значение
# И так далее
```

### 3.1: Блок Unit

| Параметр | Описание | Синтаксис |
| -------- | -------- | --------- |
| `Description` | Описание нашего сервиса | Description=Описание сервиса. Кавычки не требуются |
| `Requires` | Жёсткие зависимости: эти программы должны быть запущены или если это не так, начать запускаться параллельно (нет гарантии, что запустятся раньше нас) с нами. Если не запустились - не стартуем, если упали в процессе работы - продолжаем | Requires=one.service two.service three.service |
| `BindsTo` | Самый жёсткий режим (даже жёстче, чем `Requires`): эти программы должны быть запущены или если это не так, начать запускаться параллельно (нет гарантии, что запустятся раньше нас) с нами. Если не запустились - не стартуем, если упали в процессе работы - завершаемся (единственное отличие от `Requires`) | BindsTo=one.service two.service three.service |
| `Wants` | Мягкая зависимость: желательно, чтобы эти программы работало, но если не будут или перестанут — ничего страшного | Wants=one.service two.service three.service |
| `After` | Управляет порядком загрузки: если наша программа **одновременно** запускается вместе с той, что указана в `After`. То `systemd` запустит нашу только после того как запустится (или упадёт !!!) указанная. Важно: `After` ничего не поднимает. Он вступает в игру только тогда, когда эти две службы уже запускаются (их кто-то запустил из вне: например при запуске ОС, пользователь: `systemctl start one two` и т.д.). Причём если запущена только наша служба, она не будет ждать, пока служба из `After` проснётся | After=one.service two.service three.service |
| `Conflicts` | Конфликты: наш сервис не может работать если запущены (или будут запущены) следующие процессы | Conflicts=one.service two.service three.service |

Иерархия строгости:

1. **🛑 Критическая строгость (BindsTo / Сверхжёсткая привязка)**: обязаны запуститься параллельно с нами (иначе наш не заведётся) + если уже в работе завершатся, наш процесс тоже завершится
2. **❗ Серьёзная строгость (Requires / Жёсткая привязка)**: обязаны запуститься параллельно с нами (иначе наш не заведётся), а если уже в работе завершатся, наш процесс продолжит работу (мягче, чем BindsTo)
3. **⚠️ Желательно (Wants / Мягкая привязка)**: хотелось бы, чтобы данный процесс был, но если не будет — программа не сломается. Используется для некритических зависимостей
4. **🌿 Нет защиты (After)**: начинает работать, только если наша и `After`-служба **запускаются одновременно**, в таком случаи, он запустит нашу только после того, как `After`-служба запустится (или упадёт)

🔥 Важно: если процесс прописанный в `BindsTo` или `Requires` завершится **через `sudo systemctl stop`**, то это считается обычным завершением и наш процесс (который требует его) тоже завершится. Однако, если зависимый процесс завершится через `kill` или других образом, то тут уже развилка: `BindsTo` завершает наш процесс, `Requires` продолжает

📦 Сервисы, которые можно прописывать в `BindsTo`, `Requires`, `Wants`, `After` и `Conflicts`:

1. **`network-online.target`**: сеть полностью настроена, сконфигурирована и готовая к работе. Есть доступ в Интернет
2. **`network.target`**: в системе есть сервис (например `NetworkManager`), отвечающий за Интернет, но возможно, пока доступа к Интернету нет (ведётся установка соединения, получение IP-адреса и т.п.). В большинстве случаях, если Вам нужен готовый интернет, следует написать `network-online.target`, но большинство по ошибке пишут `network.target` что на самом деле означает: "в системе лишь запущен процесс, отвечающий за Интернет, но возможно он к нему ещё не получил доступ (нет IP-адреса, ведёт переговоры с роутером, DHCP и т.п.)"
3. **`time-sync.target`**: время синхронизировано с NTP-сервером
4. **Можно указать нестандартный**: `myservice.service`, `nginx.service`, `mariadb.service`, `postgresql.service` и т.п.

🖼️ Годный лайфхак: связка `BindsTo или Requires` + `After` гарантирует, что наше приложение запустится только тогда, когда все сервисы указанные и там и там запустятся, а связка `Wants` + `After` попытается запустить указанные сервисы (и если они запустятся, то строго раньше нас), но если они не запустятся или упадут — продолжим работать:

```systemd
[Unit]
Description=Очень важный бэкенд с БД

# Если БД упала — продолжать программу опасно. Новые учётные записи, заказы — всё пропадёт. Именно поэтому BindsTo вместо Requires
BindsTo=postgresql.service
After=postgresql.service
```

или

```systemd
[Unit]
Description=Сервис, которому желательно иметь доступ в Интернет, но не критично

Wants=postgresql.service
After=postgresql.service
```

(Чтобы этот лайфхак сработал, надо чтобы нужный сервис был прописан и в `BindsTo / Requires / Wants` и в `After`)

❗ Разработчики `systemd` официально рекомендуются не использовать голые `BindsTo/Requires/Wants`, а использовать связку `BindsTo/Requires/Wants + After`

> [!EXAMPLE]- Если узнать как это работает под капотом
> И так. Если Вы здесь, то хотите разобраться, потому этот лайфхак работает. Давайте же начнём и сравним все варианты!
> 
> ##### Вариант 1: только `BindsTo / Requires`
>  Тут есть проблема: `systemd` поймёт, что Вашему процессу обязательно нужны следующие зависимости. Однако, если они не запущены, `systemd` начнёт их запуск **параллельно с Вашим процессом**. Это может вызвать проблемы: например: `postgresql.service` поднимается за 3 секунды, а наш Backend за `0.5`. В итоге, мы запустились быстрее и отправляем запросы к ещё не проснувшейся БД
>
> ##### Вариант 2: только `After`
> Казалось бы — вот оно решение! Мы запустимся только после того, как запустятся сервисы в `After`. Да, но есть два больших но:
> 
> 1. `After` работает, только если наша и службы из `After` запускаются одновременно. Они уже должны быть одновременно запущены!
> 2. Даже если первое условие выполнилось (наша и `After`-службы запустились одновременно), `After` не гарантирует что они запустятся корректно, гарантирует что только запустит их и **независимо от результата (успех / провал), потом запустит нас**
>
> ##### Вариант 3: гибрид
> Тут каждый делает свою роль. `BindsTo / Requires` гарантирует, что процесс запустится, а `After` что сначала он, потом мы! Вуаля!
>
> P.S.: для `Wants` такая же история. Его единственное отличие от `Requires / BindsTo` в том, что он не будет останавливать нас если зависимый сервис упадёт во время работы (`BindsTo`) или не стартанёт (`BindsTo / Requires`)

### 3.2: Блок Service

❗ Тут уже таблицей не обойтись. Информации и параметров настолько много, что если бы я её делал, она бы заняла пол файла, была бы нечитаемой, громоздкой и неудобной. Поэтому всё разбито по разделам

#### Параметр Type

✏️ Тип нашего процесса:

* `simple`: процесс, который должен работать бесконечно, пока его не остановят или он не упадёт (пример: telegram-bot, веб-сервер, БД и другие **долгоживующие процессы**)
* `oneshot`: процесс, который делает какое-то действие и завершается. Он **короткоживущий** (пример: скрипт очистки логов (запустился, выполнил работу, завершился), скрипт резервного копирования, проверка файловой системы и т.д.)
* `forking`: процесс, который запустился, создал дочернего процесса и завершился. Оставил дочернего процесса одного :(
* `idle`: пусть он работает, только когда когда система ничего не делает

❓ А в чём разница? На что влияет это значение? А что если я укажу для бота `oneshot`, а для скрипта обновления — `simple`? Давайте ответим на данные вопросы ниже:

> [!QUESTION]- Вопрос 1: на что влияет это значение?
> Это значение влияет на то, когда `systemd` скажет: "я сделал всё что нужно с этим процессом, пойду по другим делам"
>
> 1. Для `simple`: запустился и всё. Иду дальше
> 2. Для `oneshot`: после того, как он завершился, пойду дальше
> 3. Для `forking`: после того, как он запустился, **создал дочерний процесс**, завершился и я подобрал дочерний процесс под своё управление, пойду дальше. Если процесс с типом `forking` **не создал дочернего** и завершился, то помечается как `failed`
> 4. Для `idle`: запустился (как с `simple`), но только тогда когда система ничем не занята
>
> Также это значение влияет на то, какие настройки разрешены и запрещены. Например для `oneshot` запрещено использовать `Restart` (потому что он на то и `oneshot` (от словосочетания one shot — один выстрел), что сделал дело и завершился), можно несколько `ExecStart`. А вот для `simple` несколько `ExecStart`\`ов нельзя
>
> Если ещё углубляться, то выбор типа влияет и на управление зависимостями. Когда, при каком типе, при каком условии кто запускает из `After`, `Requires` и/или `BindsTo`. В общем жуть

> [!QUESTION]- Вопрос 2: если я укажу не то?
> Произойдёт недопонимание. `Systemd` будет делать одно, а процесс другое. Например если для Telegram-Бота указать `oneshot`, то `systemd` будет бесконечно ждать завершения этого процесса (хотя он бесконечный)

🐧 P.S.: если ещё куча других нишевых типов типа `dbus`, `notify`, `notify-reload`, `exec`, но мы разобрали основные

#### Параметр WorkingDirectory

🌿 Устанавливает директорию, в которой хранятся файлы нашего сервиса

📓 Пример: `WorkingDirectory=/home/user/projects/my_bot`

#### Параметр ExecStart

🐍 Команда для запуска сервиса. Если используется какая-либо программа (например python), необходимо указать полный путь к ней (например `/usr/bin/python3`), а не относительный (`python3` работать не будет, только `/usr/bin/python3`)

📓 Пример: `ExecStart=/usr/bin/python3 main.py`

#### Параметр User

👨 От какого пользователя запускать сервис. Не ставьте `root`, пожалуйста

📓 Пример: `User=some_user`

#### Параметр Group

👥 От какой группы запускать сервис (в связке с `User`). Также не ставьте `root`, пожалуйста. Если не знаете что ставить, ставьте то же самое, что и в `User`

📓 Пример: `Group=some_user`

#### Параметр ExecStop

🛑 Команда для остановки сервиса (выполняется при запуске `systemctl stop`). Не обязательно, если не поставить, просто пошлётся сигнал SIGTERM

📓 Пример: `ExecStop=/usr/bin/python3 stop_working.py`

#### Параметр ExecReload

🔃 Команда для `systemctl reload`. Помните, что не все сервисы поддерживают `reload`? Мы можем сделать так, чтобы наш поддерживал. Опять же таки — параметр необязательный

📓 Пример: `ExecReload=/usr/bin/python3 reread_configs.py`

#### Параметр ExecStartPre

⬅️ Команда, которую нужно выполнить перед командой из `ExecStart`:

📓 Пример: `ExecStartPre=/usr/bin/python3 checking.py`

#### Параметр ExecStartPost

➡️ Команда, которую нужно после команды из `ExecStart`:

📓 Пример: `ExecStartPost=/usr/bin/python3 post_starting_script.py`

#### Параметр ExecStopPost

➡️ Команда, которую нужно после команды из `ExecStop`:

📓 Пример: `ExecStopPost=/usr/bin/python3 post_cleaning.py`

#### Параметр Restart

🖼️ При каких обстоятельствах перезапускать сервис? Есть 4 варианта:

1. `no` (по умолчанию) — никогда не перезапускать сервис
2. `always` — всегда (будь он завершился нормально или с ошибкой)
3. `on-failure` — перезапускать только если сервис завершился с ошибкой (упал)
4. `on-success` — только если завершился корректно (специфично)

📓 Пример: `Restart=always`

#### Параметр RestartSec

🕐 Если процесс необходимо перезапустить (сработало условие из `Restart`). Сколько подождать времени (в секундах) перед перезапуском? По умолчанию 0 — что часто бывает плохо (может доходить до 10000 попыток перезапуска в секунду). Рекомендую поставить 3 или 5 секунд

📓 Пример: `RestartSec=5`

#### Параметр StandardOutput

🎺 Куда отправлять обычный текст (`print()` в питоне или `std::cout / std::print / std::println` в C++). Есть 4 варианта:

1. `journal` (по умолчанию) — в `journalctl`
2. `file:/path/to/log.file` — при каждом перезапуске очищать указанный файл и начинать запись логов с чистого листа
3. `append:/path/to/log.file` — при перезапуске ничего не очищать, просто продолжать **дописывать** логи в этот файла (отсюда и название `append`)
4. `null` — не логировать

📓 Пример: `StandardOutput=journal`

❗ Логи отправленные в `journal` можно посмотреть командой:

```bash
sudo journalctl -u name.service # Все логи
sudo journalctl -u name.service -f # В режиме реального времени
sudo journalctl -u name.service --no-pager # Сразу вывалить в терминал
```

#### Параметр StandardError

❌ Куда отправлять ошибки (`sys.stderr` в питоне или `std::cerr` в C++). Думаю, Вы уже догадались какие есть варианты:

1. `journal` (по умолчанию) — в `journalctl`
2. `file:/path/to/log.file` — при каждом перезапуске очищать указанный файл и начинать запись логов с чистого листа
3. `append:/path/to/log.file` — при перезапуске ничего не очищать, просто продолжать **дописывать** логи в этот файла (отсюда и название `append`)
4. `null` — не логировать

📓 Пример: `StandardError=journal`

❗ Логи отправленные в `journal` можно посмотреть командой:

```bash
sudo journalctl -u name.service # Все логи
sudo journalctl -u name.service -f # В режиме реального времени
sudo journalctl -u name.service --no-pager # Сразу вывалить в терминал
```

#### Параметр EnvironmentFile

🤫 Указывает путь к файлу `.env`. После этого все переменные подтянутся и можно ими пользоваться без необходимости делать `dotenv.load_dotenv()`

📓 Пример: `EnvironmentFile=/home/user/projects/my_bot/.env`

#### Параметр Environment

📝 Прописать переменные окружения сразу у `.service` файле. Можно использовать этот параметр много раз

📕 Синтаксис: `Environment=NAME=VALUE`

📓 Пример: `Environment=TOKEN=123456789`

##### Параметр MemoryHigh

⚠️ Если потребление ОЗУ стало больше или равным чем заданный лимит, то Linux делает ряд ограничений для этого процесса:

1. Очищает кэш процесса
2. Если на сервере включен SWAP, то часть данных сбрасывается на него
3. Другие алгоритмы оптимизации потребления памяти

📕 Возможно несколько синтаксисов:

* `MemoryHigh=30B` (30 байт)
* `MemoryHigh=30K` (30 кибибайтов, примечание: 1 кибибайт — 1024 байта)
* `MemoryHigh=30M` (30 мебибайтов, примечание: 1 мебибайт — 1024 кибибайтов)
* `MemoryHigh=30G` (30 гибибайтов, примечание: 1 гибибайт — 1024 мебибайтов)
* `MemoryHigh=30T` (30 тебибайтов, примечание: 1 тебибайт — 1024 гибибайтов)
* `MemoryHigh=30%` (проценты от общего ОЗУ)

🐧 Во избежание недопониманий: официально (по международным стандартам), 1 кИЛОбайт — 1000 байт, а 1 кИБИбайт — 1024 байта. Но все привыкли, что кИЛОбайт — 1024 байта, хотя официально это не так

##### Параметр MemoryMax

🛑 Если потребление ОЗУ стало больше или равным чем заданный лимит, то Linux посылает сигнал `SIGKILL` (принудительное завершение, приложение не успевает даже сохранить данные на диск). Используется как крайняя мера

📕 Синтаксис Вы и так уже знаете (`MemoryMax=цифра + B/K/M/G/T/%`)

#### Параметр CPUQuota

🔥 Указать лимит на использование процессора. Лимит указывается в процентах, распространяется на 1 ядро

📓 Пример: `CPUQuota=30%`

✏️ `50%` — половина от ядра, `100%` — целое ядро, `200%` — два ядра, `350%` — три ядра и половина четвёртого на процесс

❗ Если у Вас больше, чем 1 ядро, и Вы хотите выделить процессу больше, чем 1 ядро — не бойтесь использовать больше 100%, 120% лишь означает, что выделить первое ядро полностью и 20% от второго

#### Параметр NoNewPrivileges

🛡️ Запретить процессу (и его дочерним процессам) повышать привилегии. Это значит, что не будет работать:

* `sudo`
* `su`
* SUID/SGID-файлы (когда программу разрешено вызвать от имени другого пользователя без ввода пароля)
* другие опасные механизмы повышения привилегии

1. `yes` — запретить повышать привилегии
2. `no` — разрешить повышать привилегии (по умолчанию)

#### Параметр PrivateDevices

💾 Разрешить ли процессу читать и изменять данные на устройствах?

1. `yes` — запретить процессу получать доступ к SSD, HDD, NVME, USB, GPU, Аудиокартам, Терминалам (консолям)
2. `no` — разрешить (по умолчанию)

#### Параметр PrivateNetwork

🌐 Запретить процессу выходить в Интернет? Полезно для программ, которым не нужна сеть

1. `yes` — запретить доступ в Интернет
2. `no` — разрешить доступ в Интернет (по умолчанию)

#### Параметр ProtectSystem

📖 Какие каталоги сделать процессу только для чтения?

1. `yes` — только для чтения: `/usr`, `/boot`
2. `full` — только для чтения: `/usr`, `/boot`, `/etc`
3. `strict` — только для чтения: всё (кроме `/dev`, `/proc`, `/sys`). Если служба пишет куда-то кроме каталогов-исключений требуется настроить исключения
4. `no` — ничего не запрещать (по умолчанию)

##### Настройка исключений с ReadOnlyPaths и ReadWritePaths

🌿 Если мы выбрали строгий режим (типа `full` или `strict`), а процессу нужно работать с другими каталогами, которые не входят в стандартный список исключений для выбранного типа, то можно вручную расширить этот "белый список":

❗ Директории вписанные в `ReadOnlyPaths` / `ReadWritePaths` подтягивают за собой и все свои поддиректории

###### ReadOnlyPaths

📖 Пути, которые можно только читать:

`ReadOnlyPaths=/path/number/1 /path/number/2 /path/number/3`

###### ReadWritePaths

✏️ Пути, в которые можно и читать и писать:

`ReadWritePaths=/path/number/1 /path/number/2 /path/number/3`

#### Параметр ProtectHome

🛡️ Запретить, перевести в режим только чтения или разрешить манипуляции с каталогами `/home` и `/root` для процессов

1. `yes` — каталоги `/home` и `/root` полностью недоступны
2. `read-only` — каталоги `/home` и `/root` доступны только для чтения
3. `no` — каталоги `/home` и `/root` не защищены (по умолчанию). Если есть параметр `ProtectSystem=strict`, то он перекрывает `ProtectHome=no`. Для разрешения писать в `/home` редактировать `ReadWritePaths`

#### Параметр ProtectKernelTunables

🏛️ Перевести параметры ядра в режим только чтение. Затрагивает: `/sys`, `/proc/sys`, `/proc/sysrq-trigger`, `/proc/latency_stats`, `/proc/acpi`, `/proc/timer_stats`, `/proc/fs`. Даже если процесс под пользователем `root` — только чтение. И всё. Это жёсткое ограничение

1. `yes` — активировать защиту
2. `no` — не активировать защиту (по умолчанию)

#### Параметр ProtectClock

🕐 Запрещено менять часы. Даже если процесс под `root` — нельзя

1. `yes` — запретить менять часы
2. `no` — разрешить менять часы (по умолчанию)

#### Параметр ProtectHostname

💻 Запрещено менять имя компьютера (`hostname`)

1. `yes` — запрещено менять имя компьютера
2. `no` — разрешено менять имя компьютера (по умолчанию)

#### Параметр ProtectKernelModules

⚙️ Довольно важный параметр на котором хотелось бы сделать акцент: данный параметр позволяет **запретить загружать и выгружать модули ядра Linux**. Обычному приложению такие права не нужны, а хакеры их с удовольствием используют

1. `yes` — запретить загрузку/выгрузку модулей ядра Linux
2. `no` — разрешить загрузку/выгрузку модулей ядра Linux (по умолчанию)

#### Параметр ProtectKernelLogs

📝 Запрещает возможность писать логи от имени ядра Linux. Опять же таки, в большинстве случаях, обычному приложению не надо писать логи от имени ядра, они должны писать логи от своего имени. А хакеры могут подделать логи, чтобы усложнить расследование в ходе ИБ-инцидента, замести следы и т.д.

1. `yes` — запретить писать логи от имени ядра Linux
2. `no` — разрешить писать логи от имени ядра Linux (по умолчанию)

#### Параметр ProtectProc

> **/proc** — это каталог в Linux, в котором хранятся папки с информацией о запущенных процессах
> 
> Название папки — PID (Process Identificator) процесса, содержание — файлы с метаданными о процессе (каждый файл хранит разную информацию, файлов много)
>
> Пример:
>
> ```
> /proc
> |
> |___ (dir) 1547
> |______ (file) arch_status
> |______ (file) cmdline
> |______ (file) cpuset
> |______ (file) mountinfo
> |______ ...
> |___ ...
> ```

⚙️ Параметр `ProtectProc` позволяет гибко настроить, за какими процессами наш процесс может следить, а за какими — нет. Рассмотрим все значения:

1. `invisible` — скрывает все процессы в папке `/proc`, кроме себя и дочерних
2. `noaccess` — показывает только папки (PID\`ы), а их содержание (файлы с информацией) нет
3. `ptraceable` — очень специфичный и нишевый режим. Разрешает доступ только к себе, дочерним и **к тем процессам, к которым наш процесс может подключиться и управлять их памятью** (есть разрешение `CAP_SYS_PTRACE` или другие условия). Очень нишево
4. `default` — показывать всё (по умолчанию)

❗ Важно: `invisible` чаще используют чем `noaccess`, т.к. если процесс видит папку в `/proc`, то он ожидает, что и содержимое можно увидеть, а с `noaccess` такое не прокатывает

#### Параметр ProtectControlGroups

🐡 По умолчанию, если процесс обладает правами `root`, то он может менять лимиты для себя и других процессов в системе (на потребление RAM, CPU и т.д.)

❗ В большинстве случаев, процессу не надо менять лимиты, а вот если хакер каким-то образом получит `root`, то он сможет выделить себе не 100M ОЗУ, а хоть всю. Давайте не дадим ему это сделать! Рассмотрим возможные значения:

1. `no` — если есть `root`, процесс может читать и изменять лимиты (по умолчанию)
2. `yes` — даже если есть `root`, процесс может **только** читать лимиты. При этом он всё ещё видит какие есть процессы и какие их лимиты, просто не может вносить изменения
3. `private` — создаётся песочница, где процесс может читать и изменять лимиты **только себя и своих дочерних**. Он физически не видит других, но тем не менее, может изменить себе лимиты, и они применятся
4. `strict` — создаётся песочница, где процесс может только читать лимиты **себя и своих дочерних**. Он физически не видит других

❌ Для защиты от хакер **не подходит**:

1. `no` — тут понятно
2. `private` — да, не видит других, но может изменять лимиты себе и дочерним

✅ Для защиты от хакер **подходит**:

1. `yes` — только чтение
2. `strict` — только чтение + не видит никого

📝 Итоги:

| Параметр | Сам, дочерние | Все остальные |
| -------- | ------------- | ------------- |
| `no` | ✅ Чтение + запись | ✅ Чтение + запись |
| `yes` | 📖 Чтение | 📖 Чтение |
| `private` | ✅ Чтение + запись | ❌ Не видит |
| `strict` | 📖 Чтение | ❌ Не видит |

#### Параметр LockPersonality

👮‍♂️ Запрещает процессу возможность "притвориться" 32-х битным или сильно старым, чтобы использовать уязвимости тех времён

1. `yes` — включить защиту. Настоятельно рекомендуется включать (только если у Вас не процесс из 2007)
2. `no` — без защиты (по умолчанию)

#### Запрет к /dev/shm: опасная уязвимость, о которой многие молчат

💾 Сначала немного теории. `/dev/shm` — это общая оперативная память. Что это? Ну вот есть программа и она что-то пишет в своё личное пространство в ОЗУ. Другая программа (в целях безопасности) не может заглянуть в ОЗУ другой, а `/dev/shm` — публичное ОЗУ. Программы пишут туда что-то, а другие могут это что-то посмотреть. 

❗ Но вот проблема: по умолчанию туда можно не только читать и писать, а ещё и ЗАПУСКАТЬ. Злоумышленник может написать скрипт, поместить его в `/dev/shm` и запустить. Конечно, если у нас грамотно настроена безопасность ФС (типа `ProtectSystem=strict`, `ProtectHome=yes` и т.д.) то сильно навредить диску не получится, но можно например залить форк-бомбу (процесс, вечно копирующий сам себя) и заставить упасть сервер

📝 Полностью запретит доступ к общей ОЗУ: `InaccessiblePaths=/dev/shm`

❌ К сожалению, если ваше приложение использует общую ОЗУ, то этот параметр включать нельзя. Но для 95% повседневных приложений (простых скриптов, ботов и т.д.) — включаем!

### 3.3: Блок Install

📦 Тут довольно мало параметров. Так что справимся быстро. Напомню что блок `[Install]` отвечает на то, что делать, когда сервис был добавлен в автозагрузку (через `systemctl enable`)

#### Параметр WantedBy

📝 Довольно простой параметр: загрузи меня на **этом этапе**. Вот список основных возможных значений. Идём от самых низкоуровневых вещей к GUI:

1. `emergency.target` — запусти меня когда система находится в режиме экстренного восстановления. Очень низкий уровень, GUI нет, базовых служб почти нет. Доступно только `cd`, `ls`, и т.п. Сети и подавно нет. Файлы монтируются в режиме `read-only`
2. `rescue.target` — запусти меня когда система находится в режиме восстановления
3. `basic.target` — загрузи меня на раннем моменте инициализации системы, когда смонтированы только диски и базовые службы. Обычному приложению там особо делать ничего
4. `multi-user.target` — запусти меня когда система уже полностью загрузилась и готова к работе. Самый частый вариант. Используется в большинстве случаях
5. `graphical.target` — запусти меня когда уже поднят рабочий стол (GUI). Используется редко, т.к. на серверах в 99% случаях GUI нет

## 4. Итоговый проект: собираем TG-БОТА

❤️ Давайте вместе соберём все знания воедино и создадим `systemd-unit` для Telegram-Бота:

```systemd
[Unit]
Description=Мой телеграм-бот

# Мы попросим systemd запустить сеть, если запустится - хорошо, если нет - ничего страшного, подождём, может потом будет. У нас не такой критический сервис, при котором если нет Интернета, надо завершаться или не запускаться
Wants=network-online.target
After=network-online.target

[Service]
# Долгоживущий процесс
Type=simple

# Запускаем не от root
User=user
Group=user

# Указываем директорию, команды запуска
WorkingDirectory=/home/user/bots/cool_bot
ExecStart=/home/user/bots/cool_bot/venv/bin/python3 main.py

# Если бот упал - поднимаем, если завершился штатно (пример через команду /stop) - не поднимаем. Также поставим задержку, чтобы не злить Telegram API
Restart=on-failure
RestartSec=3

# Лимиты
MemoryHigh=500M
MemoryMax=700M
CPUQuota=35%

# Безопасность
NoNewPrivileges=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectClock=yes
ProtectHostname=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectProc=invisible
ProtectControlGroups=strict
LockPersonality=yes
InaccessiblePaths=/dev/shm

# Запрещаем всё, кроме /dev, /proc, /sys и /home/user/bots/cool_bot
ProtectSystem=strict
ReadWritePaths=/home/user/bots/cool_bot

[Install]
WantedBy=multi-user.target
```
